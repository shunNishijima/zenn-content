# Claude Codeの制限モードでスキルが消えた原因と直し方

**この記事の要点**

- Claude Codeは権限設定やサンドボックス機能により、状況次第でツールやスキルの実行を制限することがあります。
- Qiitaでは、制限モードの導入後に自作スキル47本がすべて認識されなくなったという報告があります。
- スキルが消えたときは、設定ファイルの権限範囲とスキルの配置場所を順に確認すると原因を切り分けやすいです。

## Claude Codeの「制限モード」とは何か

最近、SNSやQiitaで「Claude Code 制限モード」という言葉を見かけます。

きっかけのひとつが、Qiitaに投稿された記事です（参考: https://qiita.com/jqit_suwa/items/4183a8e97738ba45f435）。投稿者は、Claude Codeに制限的な挙動が入ったと書いています。結果として、自作していたスキル47本がまるごと0本扱いになったそうです。

ここでいう「制限モード」は、Anthropicが単一の機能名として公式に付けた呼び方ではなさそうです。権限管理（パーミッション）やサンドボックス実行など、もともとある制御の仕組みが強く効くようになった状態を指していると考えられます。実際、Claude Codeにはコマンド実行を隔離するサンドボックスの仕組みがあります。ツールの説明文には、危険を承知でサンドボックスを無効化するためのオプションも用意されています。外部コマンドやファイルアクセスを既定で絞る設計は、もとから組み込まれていたわけです。

断定できない部分は「〜のようです」と書き分けます。以下では、スキルが動かなくなったとき個人開発者がどう調べ、どう戻せるかを整理します。

## なぜカスタムスキルが動かなくなるのか

スキルは、名前・説明・実行内容を書いたファイルをClaude Codeに読み込ませる仕組みです。読み込みが止まる理由は、経験上いくつかのパターンに絞れます。

### 許可ツールの範囲が変わった

`settings.json` や `.claude/settings.local.json` には、許可されるツールやコマンドの範囲を絞る `permissions` の設定があります。ここが変わると、スキル自体は存在していても呼び出し時点で弾かれます。

### サンドボックスがファイルアクセスを遮断した

サンドボックス実行が有効な場合、スキル定義ファイルの読み込みや外部スクリプトの呼び出しが制限の外に出られません。結果として、スキルが「見えない」扱いになることがあります。

### スキルの配置先が想定とずれた

大きなアップデートのタイミングで、スキルを探すディレクトリの優先順位が変わることがあります。個人用と共有用の両方を使っている人は要注意です。片方だけ読まれる状態になっていないか、確認してください。

### 設定の読み込み順序が変わった

プロジェクト設定・ユーザー設定・組織設定が重なる環境では、どれが最終的に勝つかの優先順位が更新で変わることがあります。上位設定で許可ツールが空になっていれば、下位で47本定義していても意味がありません。

## スキルが消えたときの確認手順

障害の切り分けは、範囲の広いところから狭めていくのが早道です。

1. Claude Codeのバージョンと変更履歴を確認する
2. `settings.json` 系のファイルをすべて洗い出し、許可・拒否リストを見る
3. サンドボックス関連のオプションが意図せず変わっていないか見る
4. スキルの配置ディレクトリが正しいパスを指しているか確認する
5. 最小構成のスキルを1本だけ新規に置き、読み込まれるか試す

5番目の切り分けが特に効きます。1本も読めないなら設定側の問題です。1本だけ読めるなら、既存スキルの記述ミスや命名衝突が疑われます。

## 実際に確認してみた所感

手元の環境で、サンドボックスまわりのオプションが実際にどう見えるか確認しました。Bashツールの説明文には、サンドボックスを無効化するための明示的なフラグが用意されています。既定では何らかの実行制限がかかる前提の設計だとわかります。

一方で、47本のスキルが一斉に消えるという現象そのものを、自分の環境で再現できたわけではありません。あくまで前述のQiita記事の報告と、Claude Codeの権限まわりの設計思想を突き合わせた推測です。断定は避けますが、原因として権限範囲の変更は筋が通っています。

## デメリット・向いていない人・うまくいかないケース

制限の強化には理由があります。実行環境を絞れば、意図しないファイル削除や外部通信のリスクを減らせるからです。一方で、次のようなケースでは不便さが目立ちます。

- 自作スキルを大量に個人運用していて、権限設定を都度見直す時間が取れない人
- CI環境など、人の確認なしにスキルを自動実行させたい構成
- 組織のポリシーで許可ツールが厳格に管理されており、個人の裁量で戻せない環境

こうした場合、スキルの本数を絞る方が現実的です。共通の設定ファイルにまとめる運用も有効でしょう。制限前の状態に完全に戻すことにこだわると、復旧はむしろ長引きます。

## 今後の付き合い方

制限モードという呼び方が独り歩きしています。しかし実体は、パーミッションとサンドボックスの組み合わせです。名前に反応するより、設定ファイルの中身を定期的に棚卸しする方が実利があります。

スキルを増やすたびに、どの権限に依存しているかをメモしておくとよいでしょう。次に似た事象が起きたときの切り分けが速くなります。

## よくある質問

**Q. Claude Codeの制限モードは公式機能ですか。**
A. Anthropicが「制限モード」という名称の機能を公式発表した情報は確認できていません。権限管理やサンドボックスなど、既存の制御機構が強く効いた状態を指していると考えられます。

**Q. スキルが急に0本になったら何を最初に見ればいいですか。**
A. まず `settings.json` 系のファイルの権限設定を確認します。次にスキルの配置ディレクトリのパスを確認してください。

**Q. サンドボックス機能はオフにできますか。**
A. Bashツールなど一部のツールには、サンドボックスを無効化するオプションが用意されています。ただしリスクが伴うため、必要な範囲に限定して使うべきです。

**Q. 組織アカウントと個人アカウントで挙動は違いますか。**
A. 組織のポリシーで許可ツールが管理されている場合、個人設定より組織設定が優先されることがあります。本記事の手順は個人環境を想定しています。

**Q. スキルを47本も持つのはやりすぎですか。**
A. 本数自体に正解はありません。ただし権限設定の見直しコストは本数に比例して増えます。

**Q. 今後も同じような制限強化は起きますか。**
A. 断定はできませんが、実行環境の安全性を高める方向のアップデートは今後も続くと見るのが自然です。設定を定期的に見直す前提で運用した方が安全でしょう。

次に取るべき行動は、自分の環境の `settings.json` を今日中に見直すことです。制限が入ってから慌てて調べるより、平時に権限を棚卸ししておく方が被害は小さくて済みます。
