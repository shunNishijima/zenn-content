# AWSインフラ構築でAIと手作業をどう使い分けるか実践基準

## この記事の要点

- AWSインフラ構築では、IaCコード生成とコスト最適化の提案でAIがすでに実用段階にある
- IAM権限の設計と本番環境への反映判断は、人によるレビューと承認が必要とされている
- 障害対応の一次切り分けはAIツールで速くできるが、復旧の最終判断は人が担うケースが多い

AWSのインフラ構築にAIを取り入れる動きが広がっています。IaCコード生成からコスト最適化まで、AIに任せられる作業は着実に増えています。一方でIAM設計や障害対応の最終判断は、今も人が担うことがほとんどです。この記事ではAWSインフラ構築でAIが得意な領域と手動対応が残る領域を整理し、実務での線引きを考えます。

## AWSインフラ構築でAIが得意な領域

### IaCコードの生成とレビュー支援

Terraformや AWS CDK（Cloud Development Kit）のコードを、自然言語のプロンプトから生成する流れが定着しつつあります。Amazon Q Developerは、要件を伝えるだけでリソース定義のたたき台を作れる機能を持っています（出典: https://aws.amazon.com/jp/q/developer/features/ ）。

ゼロから書く時間を減らせる点は大きいメリットです。ただし生成されたコードは、命名規則やタグ付けルールが自社の標準とずれることも多いです。そのまま適用せず、差分を確認する工程は残ります。

### コスト最適化とリソースの見直し

AWS Compute Optimizerは、CPUやメモリの利用実績を機械学習で分析し、インスタンスタイプの見直しを提案します（出典: https://aws.amazon.com/jp/compute-optimizer/ ）。人が過去のメトリクスを1件ずつ見比べるより、傾向をつかむのが速いです。

Trusted Advisorのコストチェックと組み合わせると、遊休リソースの洗い出しも自動化しやすくなります。ここは「提案までAI、実行判断は人」という分担がすでに現実的です。

## 人の判断が残る領域

### IAM設計と権限の最終承認

AWS Well-Architected Frameworkのセキュリティの柱では、最小権限の原則をチームでレビューする重要性が示されています（出典: https://docs.aws.amazon.com/wellarchitected/latest/security-pillar/welcome.html ）。

権限設計は、事業のドメイン知識と結びついています。どの部署がどのリソースに触れるべきかは、コードだけを見ても判断できません。AIに下書きを作らせても、承認は必ず人が行う体制が必要です。

### 障害対応と本番環境への反映

異常検知そのものはAIが得意な領域です。CloudWatchの異常検知機能を使えば、通常と違うメトリクスの変化を早く見つけられます。

一方で、ロールバックするか様子を見るかの判断は、ビジネス影響を踏まえた人の意思決定に委ねられています。誤検知のリスクもあり、自動復旧を全面的に任せる運用はまだ一般的ではないようです。

## 実際に試して感じたこと

小規模なVPC構築で、Amazon Q Developerにネットワーク構成のTerraformコードを生成させてみました。サブネット分割やルートテーブルの土台は数分でできました。

ただしセキュリティグループのポート開放範囲は、要件を細かく伝えないと広めに設定されがちでした。生成後に自分で絞り込む作業は省けず、レビューの手間はむしろ増えた印象です。速さと正確さは別物だと感じました。

## AIと手動対応の使い分け早見表

| 作業 | AIの向き不向き | 理由 |
|---|---|---|
| IaCコードの下書き | 得意 | 定型構成のパターンが豊富にある |
| セキュリティグループの最終設定 | 不向き | 要件次第で許容範囲が変わる |
| コスト最適化の提案 | 得意 | メトリクス分析はAIが速い |
| IAMポリシーの承認 | 不向き | 業務知識と責任の所在が絡む |
| 障害の一次検知 | 得意 | 異常値の発見は自動化しやすい |
| 復旧手順の実行判断 | 不向き | ビジネス影響の見極めが必要 |

## デメリット・向いていないケース

AI活用がどんな現場でも有効というわけではありません。

小規模で構成がほぼ変わらないインフラでは、AIツールの学習コストの方が上回ることがあります。数台のEC2を年に数回触るだけの環境なら、手順書だけで十分な場合が多いです。

金融や医療など監査要件が厳しい業界では、AIが生成した根拠を説明できる形で残す運用が求められます。この記録の仕組みが整っていないうちは、導入を急がない方が無難です。

IaCやAWSの基礎知識がないメンバーだけでAI生成コードを運用するのもリスクがあります。誤りに気づけないまま本番適用してしまう恐れがあるためです。

## 導入を進める手順

1. 検証環境でIaCコード生成だけ試す
2. 生成コードのレビュー担当と承認フローを先に決める
3. コスト提案は自動適用せず、月次で人が確認してから反映する
4. 障害対応ではAIの検知結果と人の判断をログに残し、後から振り返れるようにする

段階を踏むことで、任せられる範囲が自然と見えてきます。

国内でも同様の切り分けを扱ったブログが話題になりました（参考: https://qiita.com/infra365/items/aa30a54fc6f0849385a7 ）。現場ごとに線引きが違う点は、共通の悩みのようです。

## よくある質問

**Q. AWSインフラ構築でAIはどこまで自動化できますか？**
A. IaCコードの下書き生成やコスト最適化の提案までは実用段階です。IAM設計の承認や本番反映の判断は、現時点では人が担う領域として残っています。

**Q. Amazon Q DeveloperはTerraformコードを書けますか？**
A. プロンプトからTerraformやAWS CDKのコード案を生成できます。ただし生成後のレビューと修正は必要です（出典: https://aws.amazon.com/jp/q/developer/features/ ）。

**Q. IAMポリシーの作成もAIに任せて良いですか？**
A. 下書き作成には使えますが、最終承認は人が行うべきです。権限設計には業務知識と責任の所在が関わるためです。

**Q. AIが生成したIaCコードはレビューなしで適用しても良いですか？**
A. おすすめしません。セキュリティグループの設定など、要件次第で調整が必要な部分が残るためです。

**Q. 障害対応にAIを使うと復旧は速くなりますか？**
A. 異常の検知は速くなる可能性があります。ただし復旧の実行判断はビジネス影響を踏まえた人の意思決定が必要です。

**Q. 小規模な個人開発でもAI活用は有効ですか？**
A. 構成がシンプルで変更頻度が低い場合は、AIツールの学習コストが見合わないこともあります。規模と変更頻度で判断するのが良さそうです。

**Q. コスト最適化の提案は自動で適用して良いですか？**
A. AWS Compute Optimizerの提案は参考情報として扱い、影響範囲を人が確認してから反映する運用が安全です。

この線引きは、チームの体制やAWSの機能アップデートによって今後も変わっていきそうです。次に触るインフラで、まずはIaCコード生成だけ小さく試してみるところから始めてみるのはどうでしょうか。
