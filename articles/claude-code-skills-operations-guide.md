# Claude Codeスキル47本運用でわかった7つの学び

**この記事の要点**

- Claude Codeのスキルは増やすほど便利になるわけではなく、47本規模になると「探し出せない」問題が主な壁になります。
- スキルのdescriptionは検索エンジンのメタ情報と同じ役割を持ち、書き方次第で呼び出し精度が大きく変わります。
- 向いていないのは「更新頻度が低い一度きりの手順」で、そうした処理はスキルよりコマンドやドキュメントの方が管理しやすいです。

こんにちは、すんです。外資系IT企業でエンジニアをしています。

Claude Codeのスキル機能を使い始めて数か月、気づけば手元のスキルは47本になりました。デプロイ手順、コードレビューの型、社内特有の命名規則チェックなど、繰り返す作業を片っぱしからスキル化した結果です。今回は「Claude Code スキル 運用」というテーマで、数を増やしてみて初めてわかったことを整理します。参考にしたQiitaの記事（[suwa_nobu氏の投稿](https://qiita.com/suwa_nobu/items/08e3bd535dbc79e0c738)）は運用ノウハウが中心でしたが、本記事では「なぜそうなるか」の構造面から解説します。

## Claude Codeのスキルとは何か

スキルとは、特定の作業手順をMarkdownファイル（SKILL.md）にまとめ、Claude Codeが必要に応じて自動的に読み込む仕組みです。ファイルの先頭に書くdescriptionが、呼び出すかどうかの判断材料になります。Anthropic公式ドキュメント（[docs.claude.com](https://docs.claude.com/en/docs/claude-code/skills)）によれば、スキルは会話の文脈とdescriptionを照合して選択される設計です。

つまりスキルは「知識の外部ファイル化」ではなく、「呼び出し条件つきの手順書」だと理解するのが近いです。この前提を忘れると、後述する問題にぶつかります。

## 47本運用してわかった7つのこと

### 1. 本数が増えると「探索コスト」が主な敵になる

スキルが10本程度のうちは、どれも記憶していて手動で選べます。30本を超えたあたりから、自分でも一覧を忘れ始めました。実際に一覧化ツールを作って棚卸しをしたところ、似た用途のスキルが3組も重複していました。これは実際に試した体験で、想像ではありません。

### 2. descriptionの書き方が呼び出し精度を決める

descriptionを「何をするか」だけ書いたスキルは、意図しない場面で呼ばれたり、逆に呼ばれるべき場面で無視されたりしました。「いつ使うか」を具体的なトリガー語つきで書いたスキルの方が、明らかに安定して動きます。

### 3. 命名は用途より「呼び出されるべき瞬間」で決める

ファイル名を機能名にすると、似た機能同士が並んだときに区別しづらくなります。「いつ発動するか」を軸にした名前の方が、後から見返したときに迷いません。

### 4. 粒度が大きいスキルは更新のたびに壊れやすい

ひとつのスキルに手順を詰め込みすぎると、片方の手順を直すたびに全体を読み返す必要が出てきます。小さく分けたスキルの方が、修正の影響範囲を把握しやすいと感じました。

### 5. 重複スキルは「静かに」精度を落とす

似た用途のスキルが2本あると、どちらが呼ばれるか予測しづらくなります。エラーとして表面化しないため、気づくまでに時間がかかりました。これは体感としての所感で、厳密な計測はしていません。

### 6. スキルとサブエージェントは役割が違う

スキルは「手順の共有」、サブエージェントは「役割ごとの独立した実行主体」という住み分けだと理解しています。手順書として使いたい処理をサブエージェント化すると、逆に複雑になりがちでした。

### 7. 棚卸しの仕組みがないと資産が負債化する

作りっぱなしのスキルは、プロジェクトの仕様変更に追随できず、いずれ誤った手順を提示するようになります。定期的な棚卸しの仕組みを、最初から組み込んでおくべきでした。

## スキル運用がうまくいかないケース・向いていない人

すべての作業をスキル化すればよいわけではありません。次のようなケースでは、スキルより別の手段が向いています。

- **一度きりの作業**: 再利用しない手順をスキル化しても、保守コストだけが増えます。
- **頻繁に仕様が変わる領域**: 更新が追いつかず、古い情報を提示するリスクの方が大きくなります。
- **チームでの用語合わせができていない状態**: descriptionの書き方に個人差が出ると、呼び出し精度がチーム全体で不安定になります。

「まずスキル化する」より「3回繰り返したらスキル化する」くらいの基準の方が、結果的に資産として残りやすいと感じています。

## 運用を安定させるためのチェックリスト

| チェック項目 | 確認内容 |
|---|---|
| description | いつ使うかがトリガー語つきで書かれているか |
| 粒度 | ひとつの手順・ひとつの目的になっているか |
| 重複 | 似た用途のスキルが既に存在しないか |
| 更新責任者 | 仕様変更時に誰が直すか決まっているか |
| 棚卸し頻度 | 月次など定期的な見直しの予定があるか |

このチェックリストは、47本を棚卸しした際に実際に使った項目をもとにしています。

## よくある質問

**Q. Claude Codeのスキルとは何ですか？**
A. 特定の作業手順をSKILL.mdというファイルにまとめ、会話の文脈に応じてClaude Codeが自動で読み込む仕組みです。descriptionが呼び出し条件として機能します。

**Q. スキルは何本くらいが適切ですか？**
A. 明確な上限はありませんが、一覧管理の仕組みがないまま30本を超えると、探索コストが目立ち始める印象です。棚卸しの仕組みとセットで増やすのが安全です。

**Q. スキルの命名規則はどう決めるべきですか？**
A. 機能名ではなく「いつ発動すべきか」を軸にすると、似た機能が並んだときも区別しやすくなります。

**Q. スキル同士が重複するとどうなりますか？**
A. エラーにはならず、どちらが呼ばれるか予測しづらくなる形で精度が落ちます。気づきにくいため、定期的な棚卸しが有効です。

**Q. スキルとサブエージェントの違いは何ですか？**
A. スキルは手順の共有、サブエージェントは役割ごとの独立した実行主体という位置づけです。手順書として使いたいものをサブエージェント化すると複雑になりがちです。

**Q. スキルはどこに保存すればいいですか？**
A. プロジェクト単位か個人設定ディレクトリ配下に置くのが一般的です。チームで共有したい手順はプロジェクト側に置く方が管理しやすいです。

**Q. スキルの効果はどう測定すればいいですか？**
A. 呼び出しの成否をログで確認する方法が基本です。厳密な定量測定の仕組みは筆者もまだ模索中で、今後の課題です。

スキルの本数を追うより、棚卸しの仕組みをいつ組み込むかの方が、次に手をつけるべき問いだと感じています。
